# FSG Bharat — Release Register

The authoritative record of what was built, what changed, and which machine has it.
**Without git, this file is your version control.** Keep it accurate or it is worthless.

`tools\Release.ps1` appends to this automatically. Fill in the rollout row by hand
when you actually copy an exe to a machine.

---

## How to answer "which build is this machine running?"

Never by filename — a file can be renamed, half-copied, or copied to the wrong
folder and still look right. Always by **SHA-256**:

```powershell
Get-FileHash "C:\FSG Bharat\FSG Bharat 0.1.5.exe" -Algorithm SHA256
```

Match the hash against the table below. `tools\Verify-Deployment.ps1` does this
for you and also checks the database schema.

## Deploying a build that changes the database

Every launch already writes to the database — this is the part people get wrong.
`ensureSchema()` runs on **every** app start, inside a PostgreSQL advisory lock,
and it does three different kinds of thing:

| What | Count | Risk |
|---|---|---|
| `CREATE TABLE IF NOT EXISTS` | 33 | none — additive |
| `ADD COLUMN IF NOT EXISTS` | 11 | none — additive, existing rows get NULL |
| `CREATE INDEX IF NOT EXISTS` | 21 | none |
| `UPDATE` on `mapped_tb` etc. | 12 | **rewrites data** (guarded by `status NOT IN ('user_override','user_approved')`, so your manual approvals survive) |
| `DELETE FROM map2` / `map3` | 2 | **removes rule rows** — narrow, targeted at specific wrong Partners' Remuneration rules |

Then `seedDefaultMapping()` refreshes default rule set `id=1` from the exe's own
bundled `Mapping_v2.xlsx`.

So there is no such thing as "deploy the exe and leave the database alone". The
question is only whether the change is safe and reversible.

### The procedure

1. **Everyone closes the app.** On every machine. The advisory lock makes
   concurrent startup safe, but you want a clean backup point.

2. **Back up first — always, no exceptions.** On the server, seconds and ~500 KB:
   ```
   "C:\Program Files\PostgreSQLin\pg_dump.exe" -h localhost -U vera_app -Fc -C -f "D:\Backups\pre_<version>.backup" vera_financial
   ```
   This backup is your entire rollback plan. Without it you cannot undo a bad
   migration, because the old exe will not remove columns the new one added.

3. **Upgrade ONE machine first** — the server. Launch it, let `ensureSchema()`
   run, and check the app opens and an existing entity's Balance Sheet still
   ties. Do not touch the other machines yet.

4. **Verify the migration landed:**
   ```
   psql -U vera_app -d vera_financial -c "\d trial_balances"
   ```
   plus `tools\Verify-Deployment.ps1` for the exe hash.

5. **Only then roll out to the clients.** All of them, same sitting — a machine
   left on the old exe writes against the new schema.

6. **Record it** in the Rollout table below.

### If it goes wrong

Restore the backup and put the old exe back:
```
"C:\Program Files\PostgreSQLin\pg_restore.exe" -h localhost -U vera_app -d vera_financial --clean --if-exists "D:\Backups\pre_<version>.backup"
```
Rolling back the exe alone is **not** enough if the migration changed data —
additive columns are harmless to an old exe, but rewritten `mapped_tb` rows are
not. Restore the database too.

### What makes a change risky

- Additive column or table — safe, no coordination needed beyond the above.
- New `UPDATE`/`DELETE` correction in `ensureSchema()` — **it runs against live
  data on first launch**. Back up, and test on a restored copy of the production
  database first if the rewrite is broad.
- Renaming or dropping a column — never do this while an older exe may still
  launch. Add the new column, migrate, and drop it a release later.

## Source snapshots

`tools\Release.ps1` zips the source that produced each exe into
`releases\fsg-bharat-<version>-source.zip` — `src/`, `package.json`,
`package-lock.json`, `Mapping_v2.xlsx`, `itr-templates/`,
`Prescribed_Format_Reference.html`, `electron.vite.config.mjs`, the Tailwind and
PostCSS configs.

That is the whole build input. To rebuild or roll back to any release: unzip it
over a clean copy of the folder, `npm install`, `npm run build`, package.

**This is the part that replaces git.** An exe you cannot rebuild is an exe you
cannot fix. Never ship a build without its snapshot.

## The one rule that matters

**One version number = one binary, forever.**

If you change a single line after building 0.1.6, the next build is 0.1.7 — never
a second, different 0.1.6. The moment two different binaries share a version
number, every bug report becomes unanswerable, and the register above starts
lying to you.

(0.1.3 was built and then superseded within the same hour on 4 Sep 2026; it got a
new number rather than being rebuilt in place, which is why it is listed here as
"do not deploy" instead of quietly becoming a different 0.1.3.)

## What this does not give you

Being honest about the trade-off, so it is a choice rather than a surprise:

- **No per-change history.** You get a snapshot per *release*, not per edit. If a
  bug appears between 0.1.5 and 0.1.6, you cannot bisect it — you can only diff two
  zips and read.
- **No blame/annotate.** "Why is this line here?" has no answer beyond the notes
  you write in this file. Write real notes.
- **No branches, no safe experiments.** Risky changes are edited directly in the
  working folder. Copy the folder before starting anything large.
- **No off-machine backup.** These snapshots live on this laptop. If the laptop
  dies, every release dies with it. **Copy `releases\` to the server or an
  external drive** — otherwise this whole scheme is one disk failure from zero.

If those limits start to bite, the git repo already exists; the only blocker was
that it is rooted at the Desktop. Re-rooting it at this folder is a bounded job
and preserves the history that is already there.

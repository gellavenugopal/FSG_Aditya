# Engagement Foundation — Implementation Plan

## Repository findings

- The existing client entity is `entities`; its reporting periods are global `financial_periods` attached through `entity_periods`. Trial balances already reference both the client entity and (optionally) that period anchor.
- Period locking/finalisation lives on `entity_periods`; existing auditors, signatories and global auditor masters are professional records, not application-user identities.
- Legacy Electron operations still own direct PostgreSQL access and expose broad operations through IPC. The engagement service now supplies a separate trusted HTTPS boundary for the new engagement routes; it does not isolate the legacy financial routes or remove the desktop's legacy DB configuration.
- Statement generation reads existing Trial Balance/mapped data and snapshots publish against `entity_periods`. Preserve those tables and values; link engagements additively.
- `entity_periods` remains the period anchor. Engagement-scoped Trial Balance imports are stored in the existing `trial_balances` / `tb_rows` tables and linked to the engagement by a separate source-metadata relation; entity-level membership is not treated as engagement access.

## Stages

1. Additive schema for firm users, firm roles, engagements, one-or-more reporting sets, memberships, access requests, audit history, and explicit legacy-period links. Keep client entities, professional masters, and `entity_periods` distinct.
2. Run engagement operations on a separate firm-hosted HTTPS service. The service owns the engagement DB connection, additive migration, password/session authentication, server-authorized first administrator setup, permission checks, restricted-safe duplicate responses, audit history, and concurrent duplicate serialization. Desktop engagement IPC is a service client and no longer runs the engagement DB handlers directly.
3. Add the engagement list, guided create flow, and overview. Drafts may be incomplete; activation is restricted to the implemented India reporting pack and validates required fields. Existing India work is linked explicitly and remains marked unconfirmed where parameters are unknown.
4. Test against disposable PostgreSQL with a representative legacy schema. Verify migration/restart, persistence, password handling, visibility/edit/finalisation permissions, access revocation, legacy links, duplicate races, audit rollback, and disclosure boundaries. Compare synthetic India figures and signing behavior using the existing financial self-tests. Document the server/client configuration and remaining legacy isolation gap.
5. Add the first protected financial slice: open an authorised engagement, import a bounded Excel workbook, and inspect its imported ledger rows. Keep mappings, journals, notes and reports unavailable until their full paths are permission-enforced.

## Security and migration boundary

The engagement HTTPS API is a firm-hosted trusted service. Only this service receives its engagement DB configuration, and the Electron engagement handlers proxy to it. With a non-loopback `ENGAGEMENT_SERVICE_URL` (or `ENGAGEMENT_SERVICE_ONLY=true` for an explicit loopback URL), desktop service-only mode skips legacy PostgreSQL initialization and does not register the legacy financial IPC handlers. That mode exposes engagement management and protected Trial Balance import/inspection only; it does not enable mapping, journals, notes or reporting.

Legacy mode remains available and still registers broad direct-database IPC without engagement authorization. Key bypasses include `src/main/ipc/tb.js` entity/TB/stock/journal operations, `mapping.js` and `mapped-tb.js` mapping and adjustments, `financials.js` statement/PDF generation, `notes.js` disclosures, `financial-periods.js` locking/finalisation, and `fs-snapshot.js` publishing. These operations can address entity-period or TB records without checking the user's membership in a particular engagement. Do not treat this slice as whole-application isolation or production-ready multi-user deployment. Migrating all legacy DB and IPC operations behind permission-enforced server APIs is still a prerequisite. Do not infer legacy ownership, partner assignment, or reporting basis.

## Implementation and verification status

- The additive schema, service-side setup/login and engagement authorization handlers, HTTPS desktop proxy, preload API, and Engagements list/create/overview screens are implemented on the feature branch.
- Desktop startup now presents first-administrator sign-up or firm sign-in before showing the existing workspace. First-admin creation returns to sign-in; administrator account provisioning is in Settings → Firm Team. Local development includes a limited database-connection setup/retry flow. This is a UI entry gate only and does not remove the documented authorization bypass in legacy financial IPC.
- Engagements and firm-team setup are grouped under Settings. Team directory positions (employee, article assistant, auditor) are separate from the server permission role; partner is a permission role and directory position. Email invitations are not implemented; administrators share generated initial passwords securely.
- Legacy trial balances already attached to the selected `entity_periods` remain on that anchor. Unlinked trial balances are listed for owner/admin review and only linked after explicit selection; trial-balance amounts and rows are not changed.
- The protected Trial Balance slice is implemented through the trusted service: engagement-scoped listing, 8 MB bounded Excel upload, required-field/amount validation, source filename/size/SHA-256 retention, immutable imports with hash-based duplicate rejection, paginated read-only ledger inspection, and an atomic TB/rows/source/audit transaction. Legacy TBs are visible only after explicit engagement linking.
- Remote service-only desktop mode uses the configured HTTPS service without opening a desktop PostgreSQL connection or registering legacy financial IPC handlers. Its engagement screen supports list/create/open plus protected import and inspection; mapping, journals, notes and report generation are not available there.
- `npm run engagement:test` passed against disposable PostgreSQL 18 with 70 assertions. It covers the HTTPS service, additive migration/repeated startup, persistence, password handling, owner/reader/editor/partner/admin/substitute permissions, access revocation, disabled users, privacy-safe duplicates/access requests, explicit legacy linking, activation/finalisation/reopening, import validation, role permissions, engagement/TB isolation, lock/finalisation rejection, duplicate and concurrent imports, restart persistence, and atomic audit rollback. It never uses the configured application DB.
- Integration testing found and corrected participant-grant parsing, date-only parsing across PostgreSQL/JavaScript time zones, and timestamp precision during reopening. The service and operational/UAT instructions are in `ENGAGEMENT_SERVICE.md`.
- India compatibility passed with synthetic records for unchanged legacy trial-balance figures/classifications/comparatives, note links, and signatory selection across migration and explicit TB linking. Earlier `tools/selftest-fs-snapshot.mjs` baseline/current comparison at `9fae9b9` passed against identical expectations: current/prior revenue, PAT/PBT/tax, Balance Sheet classifications/totals, note rows/totals and face links, auditor/signatory selections, and snapshot schema. For this slice, both `tools/selftest-fs-snapshot.mjs` and `tools/selftest-final-signing.mjs` passed serially against disposable PostgreSQL. Their first parallel run reached all assertions but hit a Windows cleanup `EPERM`; the serial reruns exited cleanly.
- The HTTPS client can be configured on a second physical desktop, but no physical two-client UAT was performed for this slice. No live DB migration, merge, or push was performed.
